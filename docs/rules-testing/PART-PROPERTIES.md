# The part-property table

`data/part-properties.json`, generated by `npm run part-properties`.

Six rules are blocked on facts about parts that a model file never states.
This table supplies what is derivable from the LDraw library plus the LDCad
shadow library, and names what is not.

## What it holds

14,491 parts — every placeable part the shadow library says something about.
Parts with no studs and no bores are omitted: they carry no fact this table
exists to record, and their description is already on `LibraryIndex` at
runtime. Emitting them added 6,200 entries and 1.3 MB to restate what the
caller already holds.

| field | meaning |
|---|---|
| `topStuds` | male System studs — round, 6 LDU, 4 tall, non-sliding |
| `heightLdu` | stud plane to anti-stud plane — a plate is 8, a brick 24 |
| `bores` | distinct female bore radii, ascending |
| `throughBore` | some bore is open at both ends rather than blind |
| `desc`, `category` | the part's description and its first word |

## Tile versus plate comes from connectivity, not from the name

The obvious way to tell a tile from a plate is to read the description. That
would be wrong, and measurably so: **30 parts disagree with their own names,
and in every case the connectivity is right.**

| part | name says | connectivity says |
|---|---|---|
| `11203` Tile 2×2 Inverted | tile | has studs |
| `15470` Plate 1×1 Round with Swirled Top | plate | no studs |
| `19727` Plate 1×2 with Cube | plate | no studs |

An inverted tile really does present studs; a plate whose top is a moulded
decoration really has none. Name-matching is wrong in **both** directions, and
`T-01` already records that LDraw part names are systematically unreliable for
slope angles. A tile, for the purposes of `L-10` and `G-01`, is a part that
presents no studs to grip — which is what the rule is about and what the shadow
data states directly.

## What it unblocks

| rule | needs | status |
|---|---|---|
| `L-10` PLATE_BETWEEN_STUDS | tile vs plate | **implemented** — `topStuds` + `heightLdu` |
| `G-01` TILE_BETWEEN_STUDS | tile vs plate | **covered** as L-10's negative case |
| `L-05` PIN_INTO_UNDERSIZED_BORE | bore classes | **unblocked** — `bores` |
| `L-01` SYSTEM_TECHNIC_HEIGHT_MISMATCH | part classes | partial — but see its note; the 0.30 LDU error is absent from LDraw, so the rule stays not-checkable regardless |
| `L-06` CONE_ON_PIN_NO_STOP | travel stops | **still blocked** |
| `L-08` PC_ON_PC_SLIDING | materials | **still blocked** |

So the table unblocks three of the six, not six. That is worth saying plainly:
the estimate that one artifact would clear all of them was too optimistic.

## What it cannot derive

- **Material** (`L-08`). LDraw carries no material data at all. Polycarbonate
  versus ABS varies by part *and colour*, and needs a BrickLink or Rebrickable
  join. Nothing in this library can supply it.
- **Travel stop** (`L-06`). The shadow library records a bore's radius and
  whether it is capped, not how far a shank may travel before it bottoms out.
- **Slope angle** (`T-01`). Needs the part's mesh, not its header or its
  connection points.

These are recorded in the table's own `notDerivable` block, so a consumer
reading only the JSON still learns why the field it wants is absent.

## Regenerating

```
LDCAD_SHADOW_DIR=/path/to/ldcad-shadow npm run part-properties
```

Takes about seven minutes: it walks the reference closure of every placeable
part. The shadow library is CC BY-SA 4.0 and is never vendored — the script
refuses to run without `LDCAD_SHADOW_DIR` rather than silently emitting a table
with no connectivity in it.

## What implementing L-10 against it taught

The table supplied the part class cleanly, and the part class turned out to be
the easy half. A first predicate using only "is it a plate, is it on edge, are
there studs either side" fired on **30.3% of real sets** — it matched every
legitimately mounted SNOT plate in the corpus. Two further constraints brought
it to 0.4%:

- **A wedge is held by friction, so it has no stud connection.** Anything with
  an edge in the connection graph is mounted, not wedged. This did nearly all
  the work.
- **"Unconnected" and "undecidable" are different claims.** Three of the first
  six surviving findings were placements whose connectivity data was simply
  missing, where absence of edges means absence of *knowledge*. Skipping those
  halved the remainder.

Worth carrying to the next rule built on this table: a part-property lookup
tells you *what a part is*, never *what is being done with it*. The second
question is where the false positives live.
